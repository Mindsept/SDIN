Une plateforme partagée.
Plusieurs façons de s’en servir.

Ce repository définit 11 briques de plateforme, des scripts de provisionnement et des templates d’applications. Il fournit un socle de développement et d’atelier ; aucune application métier n’y est implémentée.

11 services définis 3 composants d’app proposés 1 réseau partagé : core-network 0 app métier fournie

Comment lire ces documents : les services décrits viennent de la configuration et des scripts du dépôt. Les applications et le portail documentaire IA sont des exemples d’usage proposés. L’analyse porte sur les fichiers ; le fonctionnement des services n’a pas été testé en direct ici.

02 / LES CONSOMMATEURS

Choisir les services selon le besoin

Ces cinq profils sont illustratifs. Le template propose frontend, API et worker, et demande de retirer les composants inutiles.

A

Site statique ou jeu solo

Frontend seul. Aucun service métier de la plateforme n’est nécessaire par défaut.

Registry pour distribuer l’image ; Dozzle pour consulter les logs du conteneur. Ajouter un relais API si l’on choisit Umami.
B

Portail métier

Frontend + API. Postgres pour les données, Casdoor pour la connexion, OpenBao pour les secrets.

S3 si pièces jointes ; Umami si mesure des usages.
C

Traitement par lots

API + worker. Valkey Streams distribue les jobs ; Postgres conserve leur statut ; S3 héberge les fichiers.

Le frontend est facultatif. Le worker ne reçoit pas les requêtes utilisateur.
D

Assistant documentaire

Frontend + API + indexation. S3, Postgres/pgvector et APISIX pour retrouver et exploiter des documents.

Valkey si indexation asynchrone. Le RAG reste à implémenter dans l’app.
E

Dossier à valider

API + worker de workflows. Temporal coordonne les étapes, attentes longues, reprises et compensations.

Casdoor pour les acteurs ; Postgres et S3 selon les données du dossier.

Valkey et Temporal répondent à deux besoins distincts. Valkey Streams répartit des unités de travail indépendantes. Temporal conserve la progression d’un processus qui attend, réessaie ou reprend après interruption. Un besoin simple ne justifie pas automatiquement les deux.

04 / LES FRONTIÈRES À RESPECTER

Le navigateur et le backend n’accèdent pas aux mêmes services

Le frontend affiche ; l’API sert le métier

nginx sert les fichiers de la SPA. Son JavaScript s’exécute dans le navigateur, hors du réseau de conteneurs. Les noms *.internal sont destinés aux composants backend sur core-network.

Le template transmet les accès OpenBao, Valkey, Postgres et S3 à l’API et au worker. Le port exposé du worker ne sert qu’à vérifier son état.

S3 est traité comme un service externe

SeaweedFS fournit l’API S3 sans alias s3.internal. Un conteneur utilise host.containers.internal:9000 ; le navigateur ou l’hôte utilise localhost:9000.

Chaque app reçoit un bucket et une clé limitée à ce bucket. La lecture publique est optionnelle. Pour un document privé, l’app doit organiser l’accès ; le dépôt ne fournit pas ce parcours métier.

Connexion publique, analytics via l’API

Casdoor fournit l’authentification OIDC avec un client par app et une URL de retour publique. Les secrets de configuration restent côté serveur.

Pour Umami, le contrat prévoit les chemins de l’app /api/v1/_a/t.js et /api/v1/_a/send, relayés vers analytics.internal:3000. Le navigateur ne contacte pas directement l’hôte analytics.

Des capacités IA, pas un produit RAG livré

L’image Postgres contient pgvector ; chaque app doit activer l’extension dans sa propre base. Le découpage des documents, l’indexation, la recherche et la construction du contexte restent à développer.

Les routes du dépôt acheminent task:embed vers OpenAI, y compris en mode Anthropic. task:image n’est défini qu’en mode OpenAI. Les appels réels n’ont pas été vérifiés ici.

05 / DE LA PLATEFORME À UNE APP

Provisionner, puis implémenter

Prévu dans le dépôt

Des ressources propres à chaque app

  1. Adapter les templates. Nom d’app, services conservés, plage de ports et pipeline ; images publiées dans le registry local.
  2. Exécuter le bootstrap de l’app. Il crée sa base Postgres, son utilisateur, son bucket S3 et ses accès stockés dans OpenBao. Les options LLM, Temporal et analytics sont désactivées par défaut.
  3. Activer les services choisis. onboard-app.sh configure LLM et Temporal et régénère la passerelle. Le client OIDC et les identités de test ont leurs scripts dédiés ; analytics a aussi un script de création de site.
  4. Développer les parcours métier. API, workers, modèle de données, permissions et interface ; les scripts d’onboarding ne les créent pas.
Limites constatées

Un socle d’atelier à compléter

  • Développement / démonstration. Services principalement sur une seule instance, communications sans TLS interne et plusieurs surfaces d’administration sans authentification dans la configuration de développement.
  • OpenBao en mode dev. Les secrets sont en mémoire ; le provisionnement doit être rejoué lorsque cet état est perdu.
  • Attention aux ports. La convention réserve 8000–8999 aux apps, mais OpenBao utilise déjà 8200. Éviter le bloc applicatif 8200–8209.
  • Logs et quotas limités. Dozzle consulte les logs ; il ne fournit ni métriques ni traces. Le budget LLM est une limite par fenêtre de temps, pas un quota cumulatif persistant. En mode Anthropic, le budget embeddings par app ne s’applique pas ; la limite de route est partagée. La route images n’active pas explicitement le plugin de limitation de tokens.
  • Contrat upstream à réaliser. Un conteneur dédié aux flux tiers est mentionné pour l’airgap ; aucun composant applicatif upstream n’est livré dans les templates.
